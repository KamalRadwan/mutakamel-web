## Purchase retry and receipt semantics

The purchase owner confirms that an exact preview retry returns the original saved preview, including after expiry. A new explicitly requested key may obtain a fresh five-minute quote for the same unresolved preparation after current owner checks; one terminal preparation outcome still permits only one commit. The prepared codec accepts an expired original as historical evidence without granting apply eligibility. An uncertain apply retains its original request and key.

Operation GET is read-only, with no idempotency key. Its `committedReceiptRef` identifies the actual preview. Verified COMMITTED status alone does not supply financial settlement. The actual immutable receipt reader recovers the original financial facts when the original apply key or full preview is unavailable.

Core and Gateway now register both current-owner reads: `GET /api/tenant/core/v1/subscription/operations/:operationId` and `GET /api/tenant/core/v1/subscription/plan-change-previews/:previewId/receipt`. They accept exact UUIDv7 path selectors, no query/body/Company/Branch/idempotency headers, and private/no-store responses. Current owner/session/placement checks surround coherent CP snapshots. Current purchase eligibility, current prices and the original apply key are not required. Operation GET reads durable history without refreshing or advancing it; its canonical returned operation ID is the preparation row ID, including when the request selected a bound preview-operation alias. Gateway uses its normal buffered-response budget. Tenant retains the existing 4 MiB outer financial-envelope cap and separately enforces 65,536 bytes on the receipt data; this is not a 64 KiB envelope cap.

The Tenant pages `/core/subscription/operations/:operationId` and `/core/subscription/receipts/:previewId` are mounted for these actual reads, with one bounded supported-path admission.
