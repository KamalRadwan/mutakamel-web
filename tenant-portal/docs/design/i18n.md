# Internationalization

Status: **Specification**

Written: **2026-08-27**

## What this replaced

Before the rebuild: **151 inline ternaries across 38 files**, where the English
half never entered `en.ts` —

```tsx
{lang === "ar" ? t.crm.leadsManagement : "Leads Management"}
```

— so the dictionary was only half the translation surface: nothing could audit
it, nobody could find the strings, and a translator could not see them. The
sharpest case was `login/page.tsx`, **100% hardcoded Arabic** while rendering
the language toggle.

That count is now **19**, and the rule below is what holds it there. The
remaining 19 are addressed by [D16](../build/DEFECTS.md#d16--two-auth-screens-were-never-converted--fixed-2026-08-31)
and [D17](../build/DEFECTS.md#d17--the-census-baseline-was-banked-with-violations-in-it--fixed-2026-08-31).

## The zero-ternary rule

**A component never branches on language to choose a string.** Ever.

```tsx
// ✅ The only correct form
const { t } = useI18n();
<h1>{t.crm.leads.title}</h1>
```

```tsx
// ❌ Every one of these is a bug
{lang === "ar" ? "..." : "..."}
{isRtl ? t.x : "English"}
{lang === "ar" && "..."}
```

If a string is missing from the dictionary, **add it to both files** — that is
the fix, not a ternary.

`lang` is still legitimately used for: `Intl` locale selection, `dir`
computation, and physical-side computation for third-party APIs. It is never
used to pick text.

ESLint enforces this — see [enforcement.md](enforcement.md).

### The one exemption: bilingual data fields

The rule above governs **UI copy**. It does not govern **data**.

The backend returns tenant-authored records in both languages —
`nameAr`/`nameEn` on lead stages, acquisition sources, pipelines and
opportunity stages. Choosing between those two is **not** a dictionary lookup
and never can be: a tenant's own stage name is runtime data, unknown at build
time, and a translator has nothing to do with it.

```tsx
// ✅ correct — selecting between two backend data fields
localizedName(stage, lang)

// ❌ still wrong — this is UI copy and belongs in the dictionary
{lang === "ar" ? "حفظ" : "Save"}
```

**But it goes through one named helper, never an inline ternary:**

```ts
// src/lib/format/localized.ts
export function localizedName<T extends { nameAr: string; nameEn: string }>(
  item: T,
  lang: Language,
): string {
  return (lang === "ar" ? item.nameAr : item.nameEn) || item.nameEn || item.nameAr;
}
```

Three reasons the helper is mandatory rather than optional:

1. **The fallback is real.** A tenant can leave one language blank. An inline
   ternary renders an empty cell; the helper falls back to the other language,
   so a stage always has a visible name.
2. **It is greppable.** One symbol to find when the field shape changes,
   instead of fifteen scattered ternaries.
3. **It keeps the census honest** — see below.

### What this means for the census

`design:census`'s `languageTernaries` counter matches the *syntax*
`lang === "ar" ?`, so it cannot tell UI copy from data selection. Routing every
data-field case through `localizedName()` removes the syntax from feature code
entirely, which means:

**Any `languageTernaries` count above zero is a real violation again.** That is
the point of the helper — it restores the counter as a meaningful gate instead
of a number with a footnote. Tracked as
[D17](../build/DEFECTS.md#d17--the-census-baseline-was-banked-with-violations-in-it--fixed-2026-08-31).

The two legitimate uses of `lang` that remain are direction (`dir`) and locale
selection for `Intl` — neither picks a string, and neither matches the counter.

## Dictionary structure

```text
src/i18n/
  I18nContext.tsx          provider + useI18n()
  DirectionBridge.tsx      feeds dir into Radix DirectionProvider
  useLanguage.ts           useSyncExternalStore over localStorage
  dictionaries/
    en.ts                  source of truth for shape
    ar.ts                  must match en.ts key-for-key
    types.ts               Dictionary type, derived from en.ts
```

`en.ts` defines the shape. `ar.ts` is typed against it, so a missing Arabic key
is a **compile error**, not a runtime `undefined`:

```ts
// types.ts
import { en } from "./en";
export type Dictionary = typeof en;

// ar.ts
import type { Dictionary } from "./types";
export const ar: Dictionary = { /* ... */ };
```

### Namespaces

```ts
export const en = {
  common:  { /* save, cancel, delete, retry, loading, search, ... */ },
  nav:     { /* sidebar and topbar labels */ },
  auth:    { /* login, sessions, password reset */ },
  views:   { board, card, table, boardAria, cardAria, tableAria },
  status:  { /* every enum wire value → human label */ },
  fields:  { /* every DTO field name → column/label text */ },
  errors:  { /* error code → human message */ },
  crm:     { leads: {...}, customers: {...}, opportunities: {...}, ... },
  core:    { /* core workspace screens */ },
} as const;
```

Rules for keys:

- Key by **meaning**, not by English text. `t.common.retry`, never
  `t.common.tryAgain`.
- Nest by feature, one level deeper than the namespace at most.
- No key holds markup. Use placeholders and compose in the component.
- No key is built by string concatenation at the call site.

### Enum labels are dictionary entries

Every enum wire value that reaches a user needs a label in both languages,
under `t.status.*`. The wire value itself is **never** displayed.

```ts
status: {
  ACTIVE_CUSTOMER: "Active customer",   // en
  ACTIVE_CUSTOMER: "عميل نشط",           // ar
}
```

[reference/enums.md](../reference/enums.md) lists every value that needs one.
A missing label is a compile error via the `Dictionary` type, which is the
point of typing `ar.ts` against `en.ts`.

**Never translate the wire value itself.** Enum strings sent to the backend are
case-sensitive protocol, not text.

### `labels[value] ?? value` is the bug, not the safety net

The fallback reads as defensive and is not. The day the backend adds an enum
member, that member reaches an Arabic-speaking user as a bare English
SCREAMING_CASE token in a UI containing no other English — and nothing in the
build, the tests or the logs says a label is owed, so the only detection
channel is a user complaining.

`wireLabel` in `src/lib/format/wire-label.ts` is the one way to resolve a wire
value:

```ts
wireLabel(t.crmWidgets.dimensions, key, t.common.unknownCode, "crmWidgets.dimensions")
```

It makes both halves explicit. The user gets a **translated** sentence naming
the code as unrecognized — the code stays inside it, because it is the evidence
a support ticket needs, which is the same reasoning `StatusBadge` already
applied to an unmapped status. And `console.warn` fires **once per unseen
code**, deduped by `group.value`, so a 200-row table reports once rather than
200 times.

An exhaustive map is better still where the enum is closed. `wireLabel` is for
the ones source does not close.

## Interpolation

```ts
// dictionary
leadsCount: "{count} leads",

// call site
t.crm.leads.leadsCount.replace("{count}", format(total))
```

Or a small typed helper — but the placeholder token stays `{name}` in both
files so a translator can see it. Never build a sentence from fragments; Arabic
word order is not English word order, and fragment assembly produces gibberish.

### Plurals

Arabic has six plural forms. Do not hand-roll them. Where a real plural is
needed, use `Intl.PluralRules` with the active locale and give the dictionary
an object keyed by CLDR category:

```ts
leadsCount: {
  zero: "لا عملاء محتملين", one: "عميل محتمل واحد", two: "عميلان محتملان",
  few: "{count} عملاء محتملين", many: "{count} عميلاً محتملاً", other: "{count} عميل محتمل",
}
```

English supplies only `one` and `other`. Most counters in this app are
"{n} results" style and can use `other` alone — reach for full plural rules
only when the sentence genuinely reads wrong without them.

## Dates, numbers, currency

All through `Intl`, with an explicit locale. Never `undefined`.

```ts
const LOCALE = { ar: "ar-EG-u-nu-latn", en: "en-US" } as const;
```

**Arabic renders Western digits** — the `-u-nu-latn` extension. This is settled;
the reasoning is in [typography.md](typography.md#the-digit-decision--settled).
Month names and date ordering still follow the Arabic locale.

Formatters live in `src/lib/format/` and take the locale as an argument. A
component never calls `Intl` directly.

**Never a locale-conversion call with no argument.** It resolves to the
runtime's default locale, so the same build renders different separators on a
developer's laptop, a user's browser and CI. `formatBytes` exists because the
attachment-policy limit was exactly that, with the English word "bytes"
appended — `Intl`'s `style: "unit"` supplies a translated unit for both
languages instead. The census counter `localeUnawareFormatting` holds it at 0.

`formatBytes` is **the** byte formatter. A second implementation already
existed in `crm/shared/format-file-size.ts`, which is how the same quantity
came to be formatted three different ways in one product; that helper keeps its
name and its call sites and now delegates.

**Currency amounts are decimal strings.** Format from the string; never
`Number()` them.

## Page titles

Route metadata is **client-side**, and has to be. `export const metadata` is a
server-only declaration and 122 of the 125 pages are `"use client"`; language
lives in `localStorage`, so no server render can know which language to emit.
All 132 routes therefore shared the single `metadata` block in
`src/app/layout.tsx` — every tab in a user's window read the same English
string, browser history was unusable, and a bookmark recorded nothing.

Three pieces:

1. `src/app/layout.tsx` declares `title.default` and `title.template`, both
   built from the **Arabic dictionary** rather than written inline — the server
   always renders `lang="ar"`, and hardcoding the copy would create a second,
   untracked translation surface outside `src/i18n`.
2. The server layouts that *can* carry metadata (`core`, `trade`, `(fence)`,
   `login`, `tenant`) export a segment title, which flows through that template
   so the brand stays the suffix.
3. `RouteTitle` sets `document.title` per route from `NAV_SECTIONS`, and
   re-runs when the language toggles.

`routeTitleKey` reuses the navigation map rather than introducing a second
route-to-title table beside it: the sidebar label **is** the page's name, in
both dictionaries already, and a parallel table would drift the first time a
screen was renamed. Longest matching prefix wins, so a detail route inherits
its list's title.

## Accessibility strings

`aria-label`, `aria-description`, `title`, `alt`, and every live-region
announcement come from the dictionary. An icon-only button with a hardcoded
English `aria-label` is invisible to an Arabic screen-reader user.

Live regions announce in the active language — the view switcher's
"Board view, 42 leads" is a dictionary string with a placeholder.

## What is never translated

- Enum wire values sent to the backend
- Permission strings
- Error **codes** (the human message is translated; the code is not)
- UUIDs, correlation IDs, idempotency keys
- Decimal strings
- Field paths in API requests

## Server-supplied messages

The backend may localize messages from the request language. **Client behavior
branches on HTTP status and the stable error code, never on message text.** A
server message may be *displayed*, but must never be *parsed*.

## Definition of done

- [ ] Zero `lang === "ar" ?` / `isRtl ?` string ternaries in the file
- [ ] Every user-visible string resolves through `t.*`
- [ ] Both dictionaries updated in the same commit
- [ ] `ar.ts` typechecks against `Dictionary`
- [ ] Every enum value rendered has a `t.status.*` label
- [ ] Every icon-only control has a translated `aria-label`
- [ ] Numbers and dates go through `Intl` with an explicit locale
- [ ] Screen reviewed in both languages, not just Arabic
