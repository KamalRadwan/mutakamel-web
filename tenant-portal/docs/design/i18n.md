# Internationalization

Status: **Specification**

Written: **2026-08-27**

## The current state this replaces

The dictionaries are healthy: `ar.ts` and `en.ts` are 1,072 lines each and
structurally symmetric, with 301 lookup sites.

The problem sits beside them — **151 inline ternaries across 38 files**:

```tsx
// The anti-pattern. 151 instances.
{lang === "ar" ? t.crm.leadsManagement : "Leads Management"}
{isRtl ? "إعادة المحاولة" : "Retry"}
```

The English half never entered `en.ts`. The dictionary is only half the
translation surface, so nothing can audit it, no one can find the strings, and
a translator cannot see them. Worst concentrations:
`core/authentication/page.tsx` (17), the orphaned dashboard components (43
combined), `useLogin.ts` (7), `leads-workspace.tsx` (7).

And the sharpest case: **`login/page.tsx` is 100% hardcoded Arabic** while
rendering the language toggle. Switching to English changes nothing on the one
page every user must pass through.

## The zero-ternary rule

**A component never branches on language to choose a string.** Ever.

```tsx
// ✅ The only correct form
const { t } = useI18n();
<h1>{t.crm.leads.title}</h1>
```

```tsx
// ❌ Every one of these is a bug
{lang === "ar" ? "..." : "..."}
{isRtl ? t.x : "English"}
{lang === "ar" && "..."}
```

If a string is missing from the dictionary, **add it to both files** — that is
the fix, not a ternary.

`lang` is still legitimately used for: `Intl` locale selection, `dir`
computation, and physical-side computation for third-party APIs. It is never
used to pick text.

ESLint enforces this — see [enforcement.md](enforcement.md).

## Dictionary structure

```text
src/i18n/
  I18nContext.tsx          provider + useI18n()
  DirectionBridge.tsx      feeds dir into Radix DirectionProvider
  useLanguage.ts           useSyncExternalStore over localStorage
  dictionaries/
    en.ts                  source of truth for shape
    ar.ts                  must match en.ts key-for-key
    types.ts               Dictionary type, derived from en.ts
```

`en.ts` defines the shape. `ar.ts` is typed against it, so a missing Arabic key
is a **compile error**, not a runtime `undefined`:

```ts
// types.ts
import { en } from "./en";
export type Dictionary = typeof en;

// ar.ts
import type { Dictionary } from "./types";
export const ar: Dictionary = { /* ... */ };
```

### Namespaces

```ts
export const en = {
  common:  { /* save, cancel, delete, retry, loading, search, ... */ },
  nav:     { /* sidebar and topbar labels */ },
  auth:    { /* login, sessions, password reset */ },
  views:   { board, card, table, boardAria, cardAria, tableAria },
  status:  { /* every enum wire value → human label */ },
  fields:  { /* every DTO field name → column/label text */ },
  errors:  { /* error code → human message */ },
  crm:     { leads: {...}, customers: {...}, opportunities: {...}, ... },
  core:    { /* core workspace screens */ },
} as const;
```

Rules for keys:

- Key by **meaning**, not by English text. `t.common.retry`, never
  `t.common.tryAgain`.
- Nest by feature, one level deeper than the namespace at most.
- No key holds markup. Use placeholders and compose in the component.
- No key is built by string concatenation at the call site.

### Enum labels are dictionary entries

Every enum wire value that reaches a user needs a label in both languages,
under `t.status.*`. The wire value itself is **never** displayed.

```ts
status: {
  ACTIVE_CUSTOMER: "Active customer",   // en
  ACTIVE_CUSTOMER: "عميل نشط",           // ar
}
```

[reference/enums.md](../reference/enums.md) lists every value that needs one.
A missing label is a compile error via the `Dictionary` type, which is the
point of typing `ar.ts` against `en.ts`.

**Never translate the wire value itself.** Enum strings sent to the backend are
case-sensitive protocol, not text.

## Interpolation

```ts
// dictionary
leadsCount: "{count} leads",

// call site
t.crm.leads.leadsCount.replace("{count}", format(total))
```

Or a small typed helper — but the placeholder token stays `{name}` in both
files so a translator can see it. Never build a sentence from fragments; Arabic
word order is not English word order, and fragment assembly produces gibberish.

### Plurals

Arabic has six plural forms. Do not hand-roll them. Where a real plural is
needed, use `Intl.PluralRules` with the active locale and give the dictionary
an object keyed by CLDR category:

```ts
leadsCount: {
  zero: "لا عملاء محتملين", one: "عميل محتمل واحد", two: "عميلان محتملان",
  few: "{count} عملاء محتملين", many: "{count} عميلاً محتملاً", other: "{count} عميل محتمل",
}
```

English supplies only `one` and `other`. Most counters in this app are
"{n} results" style and can use `other` alone — reach for full plural rules
only when the sentence genuinely reads wrong without them.

## Dates, numbers, currency

All through `Intl`, with an explicit locale. Never `undefined`.

```ts
const LOCALE = { ar: "ar-EG-u-nu-latn", en: "en-US" } as const;
```

**Arabic renders Western digits** — the `-u-nu-latn` extension. This is settled;
the reasoning is in [typography.md](typography.md#the-digit-decision--settled).
Month names and date ordering still follow the Arabic locale.

Formatters live in `src/lib/format/` and take the locale as an argument. A
component never calls `Intl` directly.

**Currency amounts are decimal strings.** Format from the string; never
`Number()` them.

## Accessibility strings

`aria-label`, `aria-description`, `title`, `alt`, and every live-region
announcement come from the dictionary. An icon-only button with a hardcoded
English `aria-label` is invisible to an Arabic screen-reader user.

Live regions announce in the active language — the view switcher's
"Board view, 42 leads" is a dictionary string with a placeholder.

## What is never translated

- Enum wire values sent to the backend
- Permission strings
- Error **codes** (the human message is translated; the code is not)
- UUIDs, correlation IDs, idempotency keys
- Decimal strings
- Field paths in API requests

## Server-supplied messages

The backend may localize messages from the request language. **Client behavior
branches on HTTP status and the stable error code, never on message text.** A
server message may be *displayed*, but must never be *parsed*.

## Definition of done

- [ ] Every user-visible string resolves through `t.*`

- [ ] Every enum value rendered has a `t.status.*` label
- [ ] Every icon-only control has a translated `aria-label`
